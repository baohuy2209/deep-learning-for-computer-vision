## Decision 1: 3-Split vs. Fabricated 4-Split LODO Partitioning

### Context
In previous refactoring iterations, a 4-way split schema (`source_train`, `source_val`, `source_test`, `target_test`) was inadvertently introduced. The user noted this critical discrepancy:
```python
# CODE CŨ BỊ SAI: Tự ý chế thêm source_test và target_test
p_train = self.splits_dir / f"fold_{target_cohort}_source_train.csv"
p_val = self.splits_dir / f"fold_{target_cohort}_source_val.csv"
p_src_test = self.splits_dir / f"fold_{target_cohort}_source_test.csv"
p_tgt_test = self.splits_dir / f"fold_{target_cohort}_target_test.csv"
```

### Decision
Strictly enforce the authentic **3-split schema** (`train`, `val`, `test`) across split generation, data loaders, training runners, and evaluation schemas.
Each fold $k \in \{0, \dots, 5\}$ consists of exactly 3 CSV files:
1. `fold_{fold_idx}_{fold_slug}_train.csv`: 85% patient-level GroupShuffleSplit of the 5 source cohorts, balanced via class quotas $(1500, 2500)$ per grade.
2. `fold_{fold_idx}_{fold_slug}_val.csv`: 15% patient-level GroupShuffleSplit of the 5 source cohorts, preserved at natural prevalence.
3. `fold_{fold_idx}_{fold_slug}_test.csv`: 100% of the held-out cohort, preserved at natural prevalence.

Total files across 6 folds: $6 \times 3 = 18$ CSV files in `data/processed/lodo_folds/`.

### Rationale
- **Executable Source of Truth**: Inspection of `merge_dataset_lodo.ipynb` (Cell 7) and `main_model_lodo.ipynb` (Cell 23) confirms that the notebooks generate and consume exactly these 3 files.
- **Physical Repository Verification**: The existing directory `data/processed/lodo_folds/` contains precisely these 18 CSV files (and `lodo_splits_summary.csv`). No `source_test` or `target_test.csv` files exist or were ever generated by the research notebooks.
- **Evaluation Semantics**: The paper's LODO protocol is bipartite: source validation (`val`) is used for model selection and threshold calibration ($\tau^*$), while the held-out cohort (`test`) is evaluated strictly with frozen $\tau^*$.

### Alternatives Considered
- *Retaining a 4-way split by subdividing the source validation partition*: Rejected. This would alter the sample size of validation data, degrade statistical confidence for $\tau^*$ calibration, and break compatibility with pre-generated CSVs.

## Decision 2: Dual-Layer Repository Coexistence Architecture

### Context
Prior refactoring guidelines attempted to turn original notebooks into lightweight wrappers that imported implementation from `drdg`. The user explicitly overturned this directive, mandating that the 5 canonical notebooks remain complete, self-contained historical research artifacts.

### Decision
Implement a **Dual-Layer Architecture**:
1. **Original Notebook Layer**: The 5 canonical notebooks remain 100% self-contained research artifacts with zero lines of code modified or replaced by external package imports. All class definitions, functions, and inline loops remain intact.
2. **Pure-Python Layer (`drdg/`)**: A clean, modular, pip-installable Python package under `src/drdg/` that reproduces the identical algorithms, parameters, tensor operations, and data pipelines in pure Python.
3. **Equivalence Principle**: Neither layer replaces the other. They represent dual implementations of the same research logic.

### Rationale
- **Provenance & Reproducibility**: Research notebooks run in Google Colab environments with specific dependencies, hardware acceleration, and output visualization cells. Modifying them destroys historical execution traces and invalidates paper reproducibility.
- **Modularity for Extension**: The `drdg` package enables automated testing, CI/CD, modular benchmarking, and clean reuse by the scientific community.

### Alternatives Considered
- *Notebooks as thin wrappers*: Rejected per non-negotiable user instruction.
- *Discarding notebooks entirely in favor of Python scripts*: Rejected; destroys provenance.

## Decision 3: Deterministic Parity Testing Strategy

### Context
Static code reviews cannot guarantee that modular Python code produces identical numerical results to notebook code cells. Differences in random initialization, tensor shapes, broadcasting, normalization epsilon, or gradient flow can silently alter model performance.

### Decision
Build an automated **Behavioral Parity Test Suite** in `tests/parity/` using:
1. **Deterministic Fixtures**: Synthetic image tensors, patient metadata DataFrames, and patch bags generated with fixed random seeds (`seed=42`).
2. **State Dict / Parameter Transfer**: Direct copying of identical parameter weights between notebook class definitions and `drdg` modules.
3. **Tight Tolerances**:
   - Forward pass activations: Max Absolute Error $< 1\times 10^{-6}$ (FP32 CPU).
   - Loss scalar values: Max Absolute Error $< 1\times 10^{-6}$.
   - Backward parameter gradients: Max Absolute Error $< 1\times 10^{-5}$.
   - One-step training updates: Weight difference after AdamW step $< 1\times 10^{-6}$.

### Rationale
Ensures true algorithmic and numerical equivalence without relying on loose statistical approximations or compilation-only assertions.

### Alternatives Considered
- *Training full models to convergence and comparing final test QWK*: Rejected for automated CI/CD due to extreme computational requirements and stochasticity across GPU architectures.
- *Visual inspection of code side-by-side*: Rejected as insufficient for detecting floating-point edge cases.

## Decision 4: Canonical End-to-End Workflow & Artifact Flow

### Context
The repository must not be treated as a collection of disjoint scripts. The original research follows a strict 6-stage execution graph.

### Decision
Enforce and document the sequential data dependency graph:
```text
Stage 1: Raw Data Acquisition
   data/raw/<dataset_key>/
      ↓
Stage 2: Dataset-Specific Consolidation
   total_aptos.py, total_deepdrid.py, total_idrid.py, total_idrid-segmentation.py
   Outputs: aptos_total.csv, deepdrid_total.csv, idrid_total.csv, etc.
      ↓
Stage 3: Multi-Cohort Harmonization (merge-dataset.ipynb / build_master_metadata.py)
   Outputs:
     - data/raw/hybrid/native_cropped/<dataset_key>/
     - data/raw/hybrid/train_balanced_metadata.csv
     - data/raw/hybrid/val_metadata.csv
     - data/raw/hybrid/test_metadata.csv
      ↓
Stage 4A: Standard Experiments (main_model (6).ipynb) & Head Ablation (main_model_head_ablation (3).ipynb)
      ↓
Stage 4B: Six LODO Folds Generation (merge_dataset_lodo.ipynb / generate_lodo_splits.py)
   Outputs:
     - data/processed/lodo_folds/fold_{0-5}_{cohort}_{train,val,test}.csv (18 files)
     - data/processed/lodo_folds/lodo_splits_summary.csv
      ↓
Stage 5: LODO Model Training & Evaluation (main_model_lodo.ipynb / run_lodo.py)
   Outputs:
     - checkpoints/lodo_{variant}_fold_{idx}_{cohort}_best.pth
     - results/lodo/{variant}_fold{idx}_{cohort}.json
```

### Rationale
Guarantees that every intermediate file has an explicit producer and consumer, preventing broken workflows when replicating the study.

### Alternatives Considered
- *Combining merge and LODO generation into a single execution step*: Rejected. The original research executed `merge_dataset_lodo.ipynb` after `merge-dataset.ipynb` had established the harmonized native crop pool. Preserving this separation matches notebook provenance.

## Decision 5: Bipartite Result Schema and Metric Semantics

### Context
Previous refactorings created an inconsistent result schema with keys like `source_validation`, `source_test`, and `target_test`.

### Decision
Standardize result serialization on the bipartite structure defined in `main_model_lodo.ipynb` (Cell 23 & 27):
```json
{
  "fold": 1,
  "held_out_dataset": "aptos",
  "fold_slug": "aptos",
  "in_domain_val": {
    "qwk": 0.885,
    "accuracy": 0.842,
    "within_1": 0.985,
    "per_grade_recall": [0.95, 0.75, 0.82, 0.88, 0.82],
    "rdr_operating_threshold": 0.42,
    "rdr_sensitivity": 0.94,
    "rdr_specificity": 0.82
  },
  "ood_test": {
    "qwk": 0.832,
    "accuracy": 0.801,
    "within_1": 0.965,
    "per_grade_recall": [0.91, 0.70, 0.78, 0.85, 0.79],
    "rdr_operating_threshold": 0.42,
    "rdr_sensitivity": 0.91,
    "rdr_specificity": 0.80,
    "rdr_auroc": 0.932
  },
  "delta_lodo": -0.053
}
```

### Rationale
Accurately preserves the research semantics:
- `in_domain_val`: Performance on 15% source validation set.
- `ood_test`: Zero-shot performance on 100% held-out target cohort evaluated with the frozen operating threshold $\tau^*$.
- `delta_lodo`: $\text{QWK}_{\text{ood\_test}} - \text{QWK}_{\text{in\_domain\_val}}$.
No misleading or nonexistent "source_test" partition is included.
